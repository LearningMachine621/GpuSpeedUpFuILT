## 2. 路径 A：瓶颈迁移（默认开场 — 回答"讲讲你的 GPU 项目"）

```text
        ┌────────────────────────────────────────────────────────┐
        │ 问题：256-tile ILT 仿真为什么慢？（v1 = 53.07 s）        │
        └──────────────────────────┬─────────────────────────────┘
                                   ▼  直觉① 一定是 kernel 算得慢
        ┌────────────────────────────────────────────────────────┐
        │ P0.5 profile：256× H2D 占 H2D_Init 阶段 85%             │
        │ ⇒ 直觉错了：不是"算得慢"，是"GPU 在等数据"               │
        └──────────────────────────┬─────────────────────────────┘
                                   ▼
        v3  pinned + async H2D ──────────── 53.07 → 13.36 s（3.97×）
        （DMA 和 SM 是不同引擎；async 的前提是 pinned）
                                   ▼  直觉② pointwise kernel 还能再挤一挤
        ┌────────────────────────────────────────────────────────┐
        │ nsys kern_sum：fused pointwise = 0.3% GPU 时间          │
        │ FFT 链 = 50.0%（19.5 + 18.2 + 复数乘 12.3）             │
        │ ⇒ 直觉又错了：kernel 早已不是瓶颈                        │
        └──────────────────────────┬─────────────────────────────┘
                                   ▼
        microbench：24×ifft2+累加 = 1.27 ms vs 单次 fft2 = 0.029 ms（43×）
        ⇒ 不是 IFFT 慢，是做了 24 次
                                   ▼
        P0.1 线性性 24→1（数学严格等价）──── 8.96 → 2.80 s（3.20×）
        P0.3 async D2H（对称收尾）─────── 2.80 → 2.36 s
                                   ▼
        ┌────────────────────────────────────────────────────────┐
        │ 闭环：53.07 → 2.36 s = 22.5×，3 reps，raw JSON 落盘      │
        │ 瓶颈是移动的目标：H2D → launch → FFT → IFFT              │
        │ 方法论：profile → 归因 → 等价重写 → 证据落盘              │
        └────────────────────────────────────────────────────────┘
```

**故事链**（每拍一句话）：

1. **钩子**："这个项目 22.5×，但最大一笔收益不是任何 kernel，是我两次被 profile 打脸之后才找到的。"
2. **第一次打脸**：以为 kernel 慢 → H2D 占 85%，GPU 在等数据 → 数据流编排 3.97×。
3. **第二次打脸**：以为自己写的 pointwise kernel 还有油水 → nsys 一看 0.3% → 真瓶颈 FFT 链 50%。
4. **归因递进**：FFT 50% 里再看 → 24 次 ifft2 才是大头（1.27ms vs 0.029ms）→ 次数问题不是速度问题。
5. **解法**：一条线性性等式 24→1，数学严格等价，3.20×（此处埋钩子："细节我可以用路径 B 展开"）。
6. **收尾闭环**：三次"下一步做什么"全是由上一张 profile 决定的，不是我猜的——最后全部数字重跑落盘。

> 逻辑闭环点：开头问"为什么慢"，结尾答"慢的原因换了三次，每次都是 profile 指认的，且每一跳有 committed 数字"。

## 3. 路径 B：一条数学等式（深潜 — 回答"最大技术亮点是什么"）

```text
  问题：FFT 链占 50% GPU 时间，怎么优化？
     │
     ├─ 先排除错误方向：换 FFT 库 / 手写 FFT kernel
     │    └─ microbench 否掉：单次 ifft2 ≈ 0.03 ms，本身不慢
     ▼
  归因：慢在"次数"——每 tile 每 iter 24 次（ifft2 + 复数乘 + add）
     │   实测：24× ifft2+累加 = 1.27 ms（前向 fft2 的 43×）
     ▼
  数学：aerial = Σ s[k]·Re{ IFFT2(mask_fft ⊙ K_k) }      （K=24 个核）
     │   L1  实标量可进出 IFFT      s 是实 fp32 ✓
     │   L2  IFFT 线性              定义成立 ✓
     │   L3  实部可进出实加权和      s 实数 ✓
     │   ⇒ aerial = Re{ IFFT2(mask_fft ⊙ Σ s[k]·K_k) }    （1 次 IFFT）
     ▼
  前提核查（防"看起来对"）：
     · K_k 随 mask 变吗？── 不随（固定光学系统）⇒ init 预计算一次（~25ms，
       5120 个 tile-iter 全复用，8MB 常驻显存）
     · 循环里有非线性算子吗？── 没有 ✓
     ▼
  实现：5 行代码，零新 kernel / 零新硬件 / 零近似
     ▼
  三重验证（闭环）：
     · 数值：fp32 max_abs_diff ≤ 3.7e-9；fp64 ~1e-18（残差纯舍入）
     · trace：复数乘 12.3% → 0.4%（事后 nsys 复核）
     · E2E ：8.96 → 2.80 s = 3.20×（3 reps，headline_e2e.json）
     ▼
  回答开头的问题："怎么优化 FFT？"——别优化 FFT kernel，
  先问算法让 GPU 做了多少次 FFT。profiler first, kernel later。
```

**故事链**：

1. **开场**："我最大的亮点不是写了什么，是**少做了 23/24 的活**。"
2. **先排雷**：说清为什么不走"换库/写 kernel"（单次实测 0.03ms，kernel 不慢）——展示归因而不是炫技。
3. **数学三引理**：L1/L2/L3 各一句话 + 前提核查（s 实数、K 不随 mask 变、无非线性）——**前提比结论更能证明你懂**。
4. **工程落点**：combined kernel 在 init 预计算一次、常驻显存、全 iter 复用——数学优势要靠内存布局兑现。
5. **三重验证**：独立数值校验（fp32 ≤3.7e-9，fp64 确认纯舍入）+ trace 复核 + E2E 3 reps——"我不只有结果，我有三个独立证据"。
6. **可迁移性收尾**：同样的模式 = "K 个固定核的加权卷积对同一输入求和"→ multi-head attention 的 per-head 归约、多核卷积同构。

> 逻辑闭环点：以"怎么优化 FFT"开，以"答案是别优化它"收；每个推理节点（排除→归因→数学→前提→实现→验证）都有数字或代码支撑。

## 4. 路径 C：一个不报错的 bug（深潜 — 回答"遇到最难的问题是什么"）

```text
  现象：torch.cuda.graph() 捕获流水线，replay 后输出错误——且不报错
     │
     ▼ 二分定位
  eager 正确 + graph 错误 ⇒ 排除数学/实现 bug，锁定"捕获语义"
     │
     ▼ 根因
  graph 捕获运行在私有 capture stream；
  手写 kernel 的裸 <<<>>> 默认落在 default stream
  ⇒ capture 窗口内 kernel 不在捕获流里 → 被静默跳过，图里根本没有它
     │
     ▼ 修复
  4 处手写 kernel launch 全部显式传 at::cuda::getCurrentCUDAStream()
  （PyTorch 算子天然走当前流；Triton launch 自带当前流——天然安全）
     │
     ▼ 受控证明（不是碰巧修好）
  5-mode 实验：同一份代码，只切 default ↔ current stream 一个变量
     mode3  graph + 默认流   loss-rel = 1.02   FAIL
     mode5  graph + 当前流   loss-rel = 0.00   PASS
     │
     ▼ 回填生产
  FUILT_USE_GRAPH=1 整合进 v7 主循环，graph replay 116.5 ms/iter
     │
     ▼ 附赠选型结论
  "graph-safe by construction" 成为 Triton 的第三硬优势
  （另两个：开发效率、端到端只差 2.5%）
     ▼
  闭环：现象 → 二分 → 根因 → 修复 → 受控实验 → 回生产 → 反哺技术选型
```

**故事链**：

1. **钩子**："最难的 bug 是一个**永远不报错**的 bug——输出错了，但每一层都不报警。"
2. **二分**：eager 对 / graph 错 → 一句话把搜索空间从"数学错？"砍到"捕获语义错"。
3. **根因讲原理**：默认流 vs 私有 capture 流——这里是 stream 模型知识的展示位（stream 内保序、跨流并发、capture 特殊性）。
4. **修复后加一步别人没有的**："修好了我还不放心，我做了一个**只改一个变量**的 5-mode 实验"——从 fixer 到 prover。
5. **回填生产**：不是修完就扔，graph capture 重新成为主流水线开关。
6. **反哺选型**：这个 bug 直接改变了 Triton vs CUDA 的决策权重——排障结论变成架构判断。

> 逻辑闭环点：从"现象"到"根因"到"证明"到"生产化"再到"选型影响"，没有任何一环靠"我觉得"。

| 面试官问 | 走哪条 | 开场第一句 |

| "讲讲这个项目 / 你的 GPU 优化经历" | **A** | "22.5×，但最大一笔收益来自两次被 profile 打脸之后。" |
| "最大技术亮点 / 最得意的工作" | **B** | "一条数学等式，3.20×，严格等价零近似，零新 kernel。" |
